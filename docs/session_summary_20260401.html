CISCO ↔ Extreme Networks CLI Mapping Agent

Session Summary — March 31, 2026  |  Khursheed Khan, Extreme Networks SA Team  |  Shared with team via GitHub

Overview

The CISCO-EN CLI Mapping Agent is a RAG-powered web application that translates CLI commands across 6 network operating systems organized into 9 functional bins. This document covers the full journey from initial research through architecture, development, and the path to Railway deployment.

Research Journey: Google → NotebookLM → Claude

Stage 1 — Google Research

Researched the problem space: bridging Cisco CLI knowledge for an Extreme Networks SA team. Compiled CLI cross-reference guides, cheat sheets, and command comparison docs. Output: CLI_X-Ref_Guide_1.0-3.pdf, Network_CLI_Cheat_Sheet 1.docx, CISCO_EN_Commands_Mar 31 2026.docx, Google_Search_EN-CISCO_Config_March 31 2026_10am.docx.

Stage 2 — Google NotebookLM Deep Analysis

Uploaded Cisco and Extreme vendor documentation (EXOS User Guide 22.7, VOSS User Guide 9.0) into Google NotebookLM. Generated 9 per-bin command mapping tables, a deep-level cross-bin thematic analysis (27 themes across all platforms), and a full Q&A chat session that surfaced key architectural insights.

Key discovery: NotebookLM cannot handle 60,000+ individual command cells in a spreadsheet — a proper vector database was needed. This drove the PostgreSQL + pgvector architecture decision.

Stage 3 — Claude Code: Joint Architecture and Development

Brought all NotebookLM outputs to Claude Code. Together built the full application: RAG pipeline, 13-tab Streamlit UI, SBA E2E lead agent, per-bin AI guardrails, zero-hallucination policy, data ingest pipeline, and this reference library.

Key architectural principle confirmed: NotebookLM documents do NOT go into the database. Database = CLI command data (what commands exist). Prompt layer = platform reasoning rules (how to think about those commands). This separation ensures Claude is both data-driven AND architecturally aware.

RAG Pipeline (how a query flows)

  1. User types a question → classify_tag() detects functional bin via keyword scoring
  2. Query encoded to 384-dim vector by all-MiniLM-L6-v2
  3. pgvector cosine similarity search → top-K rows (threshold ≥ 0.35, tunable in sidebar)
  4. Rows formatted as context → sent to Claude with system prompt
  5. System prompt = system_master.md + matching bin_*.md guardrail file
  6. Claude formats and returns response — never invents commands

SBA E2E Design Wizard — Deployment Order

[ONBOARD] → [IF-PHYS] → [L2-SEG] → [FAB-SDN] → [L3-VIRT] → [SEC-ID] → [MGMT-OPS] → [DIAG-LOG]

Layer 2 — Per-Bin Files (injected when bin is detected)

BinCritical Extra Rule
[ONBOARD]ZTF = Fabric Engine only; Universal Hardware persona toggle explained
[SEC-ID]netlogin dot1x ≠ dot1x; TrustSec SGT ≠ ONEPolicy role (different architectures)
[SYS-INFO]NX-OS monitoring = gRPC telemetry, not SNMP polling in production
[IF-PHYS]No shutdown/no shutdown on EXOS → enable/disable ports; jumbo = global setting
[L2-SEG]No switchport mode trunk on EXOS; STP uses STPDs not per-VLAN spanning tree
[FAB-SDN]ZTF exclusive to FE; VNI ≠ I-SID ≠ NSI are separate namespaces; enable stacking-support prereq
[L3-VIRT]Dual-step ipforwarding rule — most common missed step on Switch Engine
[DIAG-LOG]l2tracetree = FE only; ethanalyzer = NX-OS only; no embedded packet capture on EXOS
[MGMT-OPS]save not copy run start; ssh2 not ssh; FE needs BOTH prompt + sys name

Zero-Hallucination Policy + Best-Guess Option

Default: Claude only outputs commands from the retrieved database rows. Absent commands → [Not in current database] or [Pending Source Verification]. VOSS/Fabric Engine is especially high-risk for hallucination — always flag unverified FE commands.

When You Want a Best Guess

Say phrases like: "best guess", "what would you try", "your best estimate", or "I understand it's unverified". Claude responds with a clearly labelled block:

### Best-Guess Response (Unverified)
⚠️ The following is my best inference based on syntax patterns and vendor
documentation I was trained on. OS versions vary — always verify against
your platform's CLI reference before applying in production.
This is NOT sourced from the verified database.

[speculative command here]

The user always decides whether to test it. OS versions change. CLI syntax evolves between releases. The database is the authoritative source.

How to Validate the Application Is Properly Tuned

How do you know Claude is actually using the RAG database and the guardrail documents — not just making things up?

Method 1 — Raw RAG Results Expander

Every AI Query response includes a 📊 Raw RAG results expander. Open it to see the exact database rows retrieved, similarity scores, and all 6 OS columns. Claude's response should match those rows. If Claude says something not in those rows — check if it came from a guardrail (acceptable) or was invented (investigate).

Method 2 — Guardrail Injection Tests

"Configure OSPF on VLAN 10 on Switch Engine"
→ Must include: enable ipforwarding vlan [name]   (L3-VIRT guardrail)

"How do I enable a port on ExtremeXOS?"
→ Must say: enable ports X   (NOT 'no shutdown')   (IF-PHYS guardrail)

"Set up BGP on Cisco NX-OS"
→ Must start with: feature bgp                     (system_master rule)

"What is zero-touch provisioning on Extreme?"
→ Must distinguish ZTF (FE) from ZTP (EXOS); state ZTF has no Cisco equivalent

Method 3 — Hallucination Probe

"Configure multicast on Fabric Engine"
→ Must return: [Pending Source Verification]
→ Confident FE commands without this label = possible hallucination

Method 4 — RAG Settings Calibration

ChangeExpected result
Raise threshold 0.35 → 0.6Fewer but more precise results
Lower top-K 8 → 3AI should acknowledge limited data when appropriate
Verified Only = ONOnly is_verified=true rows returned
Switch to Keyword modeDifferent (string-match) result set vs semantic

Method 5 — DB Browser Audit

DB Browser tab → search any command → verify it's in the DB with the correct tag and OS columns. This shows you exactly what ground truth Claude is drawing from.

Topology Generator — Planned Feature

Planned — not yet built. When the user asks to "deploy a campus network" or describes a design scenario, the E2E Wizard should show an architecture diagram in addition to generating CLI commands.

The Idea

When a user describes a network design intent (e.g., "campus network with 802.1X, OSPF uplinks, and SNMP management"), the E2E Design Wizard should:

  1. Ask clarifying questions (how many access switches? distribution layer? routed or L2 uplinks? fabric or standalone?)
  2. Generate a topology diagram showing the network layers and connections
  3. Generate the CLI script for the chosen platform across all detected bins

Campus Network Topology Example (ASCII — simplest approach)

[INTERNET / WAN] | [CORE SWITCH] / \ [DIST-SW-1] [DIST-SW-2] ← L3 OSPF / BGP uplinks / | \ / | \ [ACC1][ACC2][ACC3] [ACC4][ACC5][ACC6] ← L2 VLANs, 802.1X | | [Users/Voice/IoT] [Users/Voice/IoT] ← End devices Cisco Path: IOS-XE on access, NX-OS on core/dist Extreme Path: Switch Engine on access, Fabric Engine for campus fabric Fabric Engine: auto-sense enable → ZTF builds IS-IS/SPBM automatically

NX-OS DME Architecture

feature commands unlock DME sub-trees. Each protocol has its own sub-tree locked by default. The feature command unlocks that sub-tree enabling CLI, SNMP, NETCONF, REST simultaneously. Without it, no configuration path works.

Rosetta Stone Rule (added to system_master.md)

NX-OS requires explicit feature activation for the same functional intent that IOS-XE accepts natively. IOS-XE: router ospf 1 directly. NX-OS: feature ospf first.

NX-OS Guestshell (added to bin_sys_info.md)

On-box Linux container (CentOS). Enable: feature guestshell then guestshell enable. Runs Python 3. Access to mgmt VRF. NX-OS exclusive — no IOS-XE equivalent.

Architecture Principle: Bin = Index, Not Partition

The bin tag is a routing hint, not a data partition. The pgvector embedding finds correct rows regardless of tag. Bin can be wrong — the 6 OS columns are what matters.
