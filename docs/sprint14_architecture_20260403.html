Verbatim design session record, April 3, 2026  ·  Khursheed Khan (Extreme Networks SA) + Claude (Anthropic)  ·  Architecture converged on graph-theoretic translation matrix + semantic intent verification

It is the authoritative reference for defending the architecture to any technical or management audience.

Context & Prior Art

The CISCO-EN CLI Mapping Agent already provides line-by-line CLI lookup across 6 OS platforms (7,550 rows, RAG-powered). The Config Translator is a new, architecturally distinct capability: it takes a complete Cisco running-config — a full deployment blueprint — and produces a fully equivalent Extreme Networks configuration for the target platform, section by section, with verified syntax, topology preservation, and intent-level quality assurance.

This is not a search feature. It is a translation engine — the difference between a dictionary and a professional interpreter.

Intent Verification Agent

Khursheed's analogy: "Like a book in English that is translated into Japanese. In language, the word for word or sentence for sentence translation does not apply."

The Intent Verification Agent operates at the semantic layer — above syntax, above commands — at the level of what the network is supposed to do. A correct translation preserves every network function, not just every command.

Mathematical Framework — Graph Theory

The translation matrix is a complete directed graph G = (V, E):

// V = set of OS platforms (vertices) V = { Cisco_IOS, Cisco_IOSXE, Cisco_NXOS, ExtremeXOS, VOSS_FE, SLX_OS } |V| = 6 // E = set of translation functions (directed edges) E ⊆ V × V where (u, v) ∈ E iff u ≠ v |E| = |V| × (|V| - 1) = 6 × 5 = 30 translation pairs // Sprint 14 activates 3 edges (any Cisco → ExtremeXOS) E_sprint14 = { (Cisco_IOS, ExtremeXOS), (Cisco_IOSXE, ExtremeXOS), (Cisco_NXOS, ExtremeXOS) } // Each edge e = (u, v) is implemented as a translation function T(u,v) : Config_u → Config_v // T is not injective in general — some features in u have no equivalent in v // The intent verifier measures |loss(T)| — information not preserved

Mathematical Framework — Semantic Similarity

Intent verification uses the same embedding space as the RAG engine — cosine similarity between intent vectors:

// Each config section is embedded as a vector in semantic space embed(section_cisco) → v_src ∈ ℝ³⁸⁴ embed(section_exos) → v_tgt ∈ ℝ³⁸⁴ // Cosine similarity = intent preservation score for that section similarity(v_src, v_tgt) = (v_src · v_tgt) / (‖v_src‖ × ‖v_tgt‖) // Overall blueprint confidence = weighted mean across all intents confidence = Σ [ w_i × similarity(intent_i_src, intent_i_tgt) ] ───────────────────────────────────────────────── Σ w_i // Weights w_i reflect intent category importance // e.g. L3-Routing weight > Voice-Transport weight for data-only sites // Calibration panel = user-adjustable weight vector w

Mathematical Framework — Information Preservation

The translation quality problem is framed as information-theoretic: how much of the source configuration's functional information survives the translation?

// Define information content of a config as its set of network functions F F(config) = { f₁, f₂, ..., fₙ } // each fᵢ is an intent/function // A perfect translation T* satisfies: F(T*(config_cisco)) = F(config_cisco) // all functions preserved // In practice, T has gaps (no-equivalent features): F(T(config_cisco)) ⊆ F(config_cisco) // Information loss = features not preserved loss(T) = F(config_cisco) \ F(T(config_cisco)) // Confidence score = |F preserved| / |F total| confidence = 1 - |loss(T)| / |F(config_cisco)| // This is exactly what the Intent Verifier Agent computes

Mathematical Framework — Formal Grammar

Cisco IOS configuration follows a context-free grammar (CFG). The parser implements a recognizer for this grammar, enabling deterministic section extraction regardless of prose mixed into the input file.

// Simplified CFG for Cisco running-config Config → Device* Device → GlobalCmd* Section* Section → SectionHdr SubCmd* SectionHdr → "interface" ID | "router" PROTOCOL ID | "vlan" NUMBER | "ip" "dhcp" "pool" NAME | "line" TYPE RANGE | "router" "bgp" NUMBER "address-family" ... SubCmd → INDENT CiscoKeyword Args GlobalCmd → CiscoKeyword Args // no indentation // The parser walks the token stream top-down // Indent level 0 = global or section header // Indent level 1+ = sub-command body // Prose lines (not matching CiscoKeyword) are classified as context text

Architecture Defence Brief

If asked to justify this architecture to a technical or management audience, the argument rests on four principles:

1. Graph-Theoretic Completeness

The 6-OS translation matrix is a complete directed graph with 30 edges. Each sprint implements a subset of edges. The architecture is open-closed: new platforms are added by implementing new edges (translation agents), without modifying existing ones. Sprint 14 → 17 implements 12 of the 30 edges covering the highest-value migration paths (Cisco to EN and back).

2. Semantic Fidelity over Syntactic Matching

Syntactic matching (dictionary lookup) fails for cross-platform translation because platforms are not isomorphic — EXOS has no interface sub-mode, VOSS has IS-IS fabric constructs with no Cisco equivalent. The intent verification layer operates in semantic embedding space, measuring functional equivalence rather than textual similarity. This is the same mathematical principle as the RAG engine but applied at the config-block level rather than the command level.

3. Information Preservation as a Measurable Property

The confidence score is not subjective — it is the ratio of preserved functional intents to total functional intents, weighted by category importance. The calibration panel makes the weight vector user-adjustable, allowing the SE team to tune the threshold to their specific deployment risk tolerance. This is auditable and reproducible.

4. Incremental, Testable Build

Each phase builds on verifiable foundations: the parser is testable in isolation (input: raw config string, output: typed section list). The translate agent is testable against the RAG DB. The intent agents are testable by comparing expected vs actual intent maps. The topology builder is visual and immediately auditable. No phase requires the next to be complete before it can be validated.
